# 归档功能分析报告

> 分析日期：2026-05-25
> 分析范围：todo-tui 工程 src/ 目录

## 一、归档功能代码位置

**结论：当前工程不存在归档功能。**

通过搜索以下关键词均无匹配结果：
- `archive` / `backup` / `history` / `restore` / `snapshot` / `export` / `import`

涉及的文件路径及函数名（无归档相关代码）：

| 文件 | 相关函数 | 说明 |
|------|----------|------|
| `src/storage/mod.rs` | `insert_todo`, `update_todo`, `delete_todo`, `list_todos` | 仅支持 CRUD，无软删除或历史记录 |
| `src/app.rs` | `delete_selected`, `toggle_status`, `cancel_todo` | 删除为物理删除，状态切换仅 Pending/Done/Cancelled |
| `src/main.rs` | `run` (主循环) | 无定时归档或数据导出逻辑 |
| `src/models/todo.rs` | `Todo` 结构体 | 无 `deleted_at`、`archived` 等字段 |

## 二、数据流描述（从触发到完成）

**当前无归档数据流。** 删除操作的数据流如下（作为对比）：

1. **触发**：用户在 Normal 模式下按 `d` 键，或 Detail 模式下按 `d` 键
2. **确认**：进入 `AppMode::DeleteConfirm` 模式，等待用户按 `y` 确认
3. **执行**：`delete_selected()` 调用 `storage.delete_todo(id)`
4. **持久化**：执行 `DELETE FROM todos WHERE id=?` SQL 语句
5. **内存同步**：从 `self.todos` 中移除该 todo，调整 `selected_index`
6. **完成**：返回 Normal 模式

**特点**：物理删除，数据不可恢复。

## 三、问题列表（潜在问题或改进点）

### 问题 1：物理删除导致数据不可恢复
- **描述**：删除操作直接执行 `DELETE FROM todos`，被删除的数据无法找回。用户误删后无任何恢复手段。
- **影响**：数据安全性低，用户信任度下降。
- **建议**：引入软删除机制（添加 `deleted_at` 字段），或提供回收站功能。

### 问题 2：无数据导出/备份功能
- **描述**：数据库文件存储在 `~/.config/todo-tui/todos.db`，用户无法导出数据为 JSON/CSV 等可读格式，也无法手动备份。
- **影响**：数据迁移困难，重装系统或切换设备时数据丢失。
- **建议**：增加 `export` 子命令（JSON/CSV），或提供自动备份到指定目录的功能。

### 问题 3：无历史记录/操作日志
- **描述**：每次修改（状态切换、编辑）直接覆盖数据库，不保留修改历史。用户无法查看某个 todo 的变更记录。
- **影响**：无法追溯任务状态变更历史，审计能力缺失。
- **建议**：引入操作日志表（`todo_history`），记录每次状态变更的时间、旧值、新值。

### 问题 4：无自动归档过期任务机制
- **描述**：已完成（Done）或已取消（Cancelled）的任务与待办任务混在一起，只能通过筛选面板手动过滤。无自动将过期任务移出主列表的机制。
- **影响**：随着时间推移，已完成任务堆积，影响主列表浏览效率。
- **建议**：增加自动归档策略（如完成超过 30 天的任务自动移至归档表），或提供一键归档已完成任务的功能。

### 问题 5：无数据导入功能
- **描述**：仅有 `add` 子命令支持 CLI 添加单条任务，无批量导入功能。
- **影响**：从其他工具迁移数据时需要手动逐条添加，效率低下。
- **建议**：增加 `import` 子命令，支持从 JSON/CSV 文件批量导入任务。

## 四、总结

todo-tui 当前是一个轻量级本地待办事项管理工具，专注于核心 CRUD 操作。归档、备份、历史记录等数据管理功能完全缺失。若需要增强数据安全性和可用性，建议优先实现软删除（问题 1）和数据导出（问题 2），这两项对用户体验影响最大。
